## 实机条件

一台 M1 MacBook Pro、一台 Windows x64 工作站和当前 USB3 线/端口。Windows 显示收发链路均为 5 Gbps；此值不是应用吞吐量。USB2、其他机器或端口未在本轮复测。

工作站保持离线，使用独立网线管理。Secure Boot 原已关闭、测试模式原已开启，HVCI 保持运行；没有修改这些安全策略。Windows 电源方案保持原 GUID `381b4222-f694-41f0-9685-ff5bb260df2e`。Mac 配件策略按维护者先前设置保持“始终允许”，本轮没有锁屏操作或权限更改。

测试明确绑定 USB 两端地址，未使用 SMB 多通道。Mac USB MTU 为 1500，Windows 为既有 8000；本轮没有更改 MTU、IP、路由或电源方案。传输不触及 Windows D 盘。只有临时、限 USB 地址与接口的测试端口规则，结束后删除。

## 新包检查结果

- 正常 `pnputil /add-driver ... /install` 返回 0，绑定为本机 `oem66.inf`；此编号不能复制到其他机器。
- 父设备 PnP OK、problem code 0、服务 Running；实际加载 SYS 与上述签名哈希一致。旧 `oem65.inf` 已导出回滚材料。
- 注册表实验开关仍缺失，按默认 mode0 运行；没有开启恢复模式 2/3。
- 四轮交替上传/下载，每次 64 MiB，共每方向 256 MiB，八次 SHA256 校验全通过。
- 接收端有效载荷计时：Mac→Windows 201.8–204.6 MB/s，Windows→Mac 390.6–401.5 MB/s。短内存测试包含 CNG 哈希开销，不代表 SMB、落盘速度或长期性能承诺；两个方向分别使用接收端时钟，没有直接相减两台机器的时间。
- 32 MiB 上传到真实 C 盘文件，八块校验、`Flush(true)`、全文件读回 SHA256 校验通过，测试载荷已删除。
- 一次精确父设备 PnP 重启返回 0，随后指定 USB 源地址的三次 ping 全通过。这不是 D0→Dx→D0 休眠测试。
- 重连后独立新 RunId 再做一轮双向 16 MiB，两次 SHA256 校验通过，两次连接均首次成功。服务器结束后监听器和临时规则清理完成。

本地完整 portable 测试通过，包括恢复探针 832 checks / 0 failures；它们是模型和源码检查，不是 Windows 内核验证。

## 能力门槛与未完成部分

只读工具读取到 Mac 配置 `bmAttributes=0xC0`，未设置远程唤醒位；Windows 电源数据为支持 D0/D3、wake from D0。云端评审也认为仅改 `IdleUsbSelectiveSuspend` 不够。因此没有强制挂起，也没有宣称入站网络唤醒可用。完整方案见 [POWER_MANAGEMENT](POWER_MANAGEMENT.zh-CN.md)。

维护者确认此前首次 USB3 错误来自旧线，锁屏重连来自 Mac 配件授权。本轮不继续重现这两项，也不把历史失败删除或改成通过。新包的实验终态故障恢复、持锁链路通知重入、真正睡眠/唤醒、USB2、锁屏、长时间传输和内存增长仍未验收。

## 失败的准备步骤

保留了三项测试工具/编排失败，不归为驱动传输失败：签名脚本单元素数组取到了盘符首字符，签名前失败且私钥已清除；C 盘 worker 的第二处固定路径未同步，路径门槛拒绝且未开始传输；重连后第一次服务器等待到期，没有客户端数据连接。修正后使用独立新 attempt/RunId，不覆盖旧证据。

原始证据私存于维护项目 `artifacts/idle-release-20261010`，不公开含设备序列号的日志。发布只包含脱敏结论、精确产物身份和文件校验值。
