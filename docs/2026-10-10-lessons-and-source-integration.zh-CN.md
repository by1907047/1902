# USB 网卡经验总结与源码整合

## 当前结论

新线和新 Mac 端口一起更换后，原驱动默认模式完成一次十分钟双向传输，没有应用超时、断连或 SHA256 校验失败。这使物理连接路径更值得怀疑，但不能单独认定旧线损坏：线和端口同时变了，也没有做分开对照。按维护者要求，本轮停止进一步实机验证，转为源码整合、构建和回归。

管道恢复解决的是出错后持续停滞，不是首次 USB 事务错误的根因。恢复功能仍默认关闭，源码合并不表示已获得长期稳定性、锁屏自动重连或正式签名认证，也不自动替换工作站已安装的驱动。

## 已整合的改进

PR1 提供 USB2/USB3 速率类别报告、NTB 参数校验、重复 PrepareHardware 内存释放、接收队列上限和有界错误日志。main 已有独立 NTB 保留字段清零和循环 NDP 链拒绝，本轮保留这些改动及其测试，没有用实验分支覆盖它们。

PR3 提供默认关闭的发送诊断、管道级恢复、收发恢复串行化、发送准入保护及有界补充恢复额度。只重置管道，不自动重置设备或端口，不重放旧有效载荷。复位请求有2秒超时，但等待底层取消完成不因此具备整个恢复过程的硬超时。

本轮补充终态报告：在恢复模式中，IN/OUT 启动失败、管道复位后未能重启或 IN 已确认设备消失时，报告链路断开，并抑制重复通知。随后两个管道都成功启动，才恢复“已连接”；正常排队停止不触发此报告。空闲时没有 OUT 成功不等于故障，不采用“三秒无发送就断网”。链路恢复报告只代表管道就绪，实际传输成功仍需业务证据。

该改动通过既有适配器回调使用 [NetAdapterSetLinkState](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/netadapter/nf-netadapter-netadaptersetlinkstate)，不增加 PnP 重启、定时健康探测或安全设置修改。模式0/1不执行新链路报告；模式0数据路径仍与冻结 PR1 的 I/O 模型逐事件比较。

## 排查经验

- 先确认真实端口和速率，再讨论线材升级。Mac 换端口可能改变 enX 编号，不能永久写死 en4；还要核对地址、MTU、来源路由和独立管理链。
- 区分第一次事务错误、随后的连续超时、恢复尝试及真正的新请求成功。Connected、PnP OK 或复位 API 返回成功不能代替业务校验。
- 用共同 run ID、方向、请求代际和单调时间关联状态链。两台电脑约一分钟的墙钟差不能用于微秒级因果排序。
- 记录每方向有效载荷和观测范围。环形日志无异常、600秒业务通过及完整物理层零错误，不是同一个结论。
- 文件上限不等于捕获内存上限，探针退出异常不应归为驱动故障。优先采用有界、低开销且可清理的采集。
- 保留失败和历史版本，不把后续成功追溯成旧版本已合格。编译、模型回归、实机传输和微软签名分别验收。

## 云评阅中需要收紧的判断

电源模式与吞吐相关，不足以证明高频 U1/U2 切换，更不能直接解释 OUT 的首次 XACT；这里“上传”是 Mac→Windows，即 Windows USB IN。短时间复发也不能排除物理路径。NTB 格式错误与 USB 事务错误属于不同观测层，但不能据此绝对排除设备固件受异常请求影响。Linux 对照目前没有执行。

本轮不缩短恢复冷却、不用一次发送成功无限补充额度，也不扩大未经验证的 OUT 错误码恢复范围。避免把容错变成重置风暴。首次故障现场冻结、更细请求关联、睡眠唤醒、持续负载和正式签名仍是后续事项，不作为本轮已完成内容。
